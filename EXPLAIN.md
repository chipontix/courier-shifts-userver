# EXPLAIN: как устроен courier-shifts-userver и что в нём доказано

Документ для Рабии: чтобы уверенно рассказать проект на собеседовании и повторить любую цифру из README.

## 1. Как устроено и почему так

**Сервис.** HTTP API на userver (C++20): курьеры, смены, доставки, заработок. Код в двух файлах:
`src/handlers.cpp` (ручки, SQL, кэш) и `src/earnings.cpp` (правила оплаты, ключи dynamic config).

**Инвариант «смены курьера не пересекаются» живёт в базе, а не в ручке.** В `postgresql/schemas/db.sql`
стоит `EXCLUDE USING gist (courier_id WITH =, period WITH &&) WHERE (cancelled_at IS NULL)`. Почему не
проверка в коде: `SELECT EXISTS`, а потом `INSERT` — это check-then-act. Два параллельных запроса оба видят
«пересечений нет», и оба вставляют. Тест `tests/test_race.py` это поймал: 4 пересекающиеся смены из 16
в одном раунде (`docs/race-before-constraint.txt`).

**Advisory lock на курьера.** С exclusion constraint параллельные вставки ждут незакоммиченные строки друг
друга, и Postgres убивает часть из них с `40P01 deadlock detected`. Ретрай не помог: при 16 конкурентах
проигравшие снова дедлочились между собой. `pg_advisory_xact_lock(courier_id)` в CTE того же запроса
выстраивает писателей одного курьера в очередь без лишнего round trip. Проигравший видит закоммиченную
строку и получает честный 409.

**`FOR SHARE` на строке смены при записи доставки,** чтобы параллельная отмена смены не проскочила между
проверкой «смена активна» и вставкой доставки.

**Кэш заработка по курьеро-дням в Redis.** Ключ `earnings:{courier}:<день>`, чтение одним `MGET`,
недостающие дни одним range-запросом и `SET EX`. Запись инвалидирует только свой день. Деньги считаются на
каждый запрос из агрегатов, поэтому смена тарифа в dynamic config не требует сброса кэша. Если Redis лежит,
сервис читает из базы (кэш best effort).

**Dynamic config** (`COURIER_TARIFFS`): тарифы меняются без рестарта, testsuite подменяет их на тест.

**Congestion control** включён в продовом конфиге (`CPU_LIMIT=2c`), а для замеров ёмкости его выключает
`CC_ENABLED=false`.

**Почему так, а не иначе (коротко):** инварианты в БД, потому что только база видит все транзакции;
advisory lock, потому что ретраи не сходятся; кэш по дням, потому что флеймграф показал низкий hit rate
у кэша «на курьера целиком».

## 2. Что ломалось и как нашли

1. **Гонка при проверке пересечений в ручке:** нашёл `tests/test_race.py` (16 параллельных запросов,
   10 раундов, ровно один 201). Лечение: exclusion constraint.
2. **Дедлоки 40P01 → 500:** нашёл тот же тест, запущенный под TSan. Лечение: advisory lock.
3. **Сервис не стартовал вне testsuite:** `http-client` зависел от `http-client-core`, который был
   подключён только в testsuite. Нашёл стенд нагрузки в продовом конфиге (коммит `de0f6bb`).
4. **`CPU_LIMIT=2` молча игнорировался** (userver ждёт `2c`), и congestion control работал в fake-mode.
   Нашёл стенд нагрузки (коммит `de0f6bb`). Корень оказался в самом userver, см. раздел 4.
5. **`nofile=1024` в контейнере** дал `EMFILE` и падение под тысячами соединений Pandora. Подняли лимит.
6. **CI asan:** `StackUsageMonitor` требует userfaultfd, а GitHub Actions его не даёт (EPERM). В Debug это
   assertion. Монитор выключен только в testsuite-конфиге (коммит `915875a`).
7. **TSan:** два узких suppression на отчёты внутри userver (shutdown в `~Manager` и `ClusterTopology` в
   Redis standalone). Обоснование в `tsan.suppressions.txt`.
8. **Флеймграф:** ручка заработка занимала 19% CPU сервиса, Redis-счётчики показали hit rate 17%. Лечение:
   кэш по дням. Результат: −12% CPU на 12k RPS.

## 4. Фикс в userver

**Что нашли.** `hostinfo::CpuLimit()` в userver начиная с v2.16 (коммит `b0efc2b49`, фолбэк на cgroup v2)
возвращает 0 вместо «лимита нет». Из-за этого `IsInRtc()` всегда true, и congestion control с дефолтным
`only-rtc: true` перестал падать при старте без `CPU_LIMIT`: он молча уходит в fake-mode. Ровно это
случилось у нас с `CPU_LIMIT=2`. Второй баг там же: лимит из cgroup обрезается до целого
(`--cpus=1.5` → 1, `--cpus=0.5` → 0).

**Как нашли.** Разбирали баг 4 из README: почему опечатка в `CPU_LIMIT` не валит сервис, хотя код CC
должен бросать исключение. Прочитали `congestion_control/component.cpp` → `hostinfo::IsInRtc()` →
`cpu_limit.cpp`, сравнили с версией до `b0efc2b49`.

**Что сделано.** Ветка `fix-hostinfo-cpu-limit` в `chipontix/userver`: коммит с тестом (`800c60d46`,
оба случая падают) и коммит с фиксом (`c4bc0dc6a`, проходят, весь `userver-universal-unittest` зелёный).
Чтобы функцию можно было тестировать, пути к `/proc/self/cgroup` и `/sys/fs/cgroup` стали параметрами
внутренней `hostinfo::impl::GetCpuLimit()`. Публичный API не изменился. Текст PR и правила контрибуции в
`UPSTREAM-PR.md`. PR не открыт: открывает Рабия.

**Что мешало при сборке на маке** (к фиксу не относится): brew-шный OpenSSL 4.1 ломает
`crypto/certificate.cpp`, а re2 2023-03-01 не собирается с ICU 78. Собирали с заголовками OpenSSL 3.6
и локальным re2 без ICU. Clang выкидывает `-I`, если тот же каталог (даже через симлинк) уже есть
в `-isystem`, поэтому заголовки OpenSSL 3 пришлось скопировать. Ещё 4 теста `formats::json` иногда
падают и на чистом `develop`: они плавающие, это отдельная тема, её не трогали.

**Влияет ли на проект.** При текущем конфиге нет: `CPU_LIMIT=2c` задан явно, `only-rtc: false`, CPU
выделены через cpuset, а не квоту. Поэтому проект остался на userver 3.2.

**Второй фикс: сборка с OpenSSL 4** (ветка `fix-crypto-openssl4`, коммиты `ed25e63c1` — тест на
`Certificate::GetSubject()`, `26961335c` — фикс). Нашёлся, пока собирали первый фикс: brew-шный `openssl`
стал версии 4.1, и `userver-universal` перестал собираться. Причин две.
1. `X509_get_subject_name()` теперь возвращает `const X509_NAME*`. Лечится словом `const`: функция печати
   принимает const ещё с OpenSSL 1.1.
2. В OpenSSL 4 удалили ENGINE API. Заголовок остался, поэтому код компилируется, но падает линковка.
   Лечится `#ifndef OPENSSL_NO_ENGINE`: этот макрос OpenSSL сам определяет, когда движков нет.
С OpenSSL 4.1 весь `userver-universal-unittest` проходит (2161 тест), с заголовками OpenSSL 3.6 оба
изменённых файла компилируются. `core` с OpenSSL 4 не собирали. Проект не затронут: в его образе
Ubuntu 24.04 стоит OpenSSL 3.0.

## 5. Десять вопросов с собеседования

1. **Почему пересечения смен проверяет база, а не код?** Проверка в коде — это check-then-act: между
   SELECT и INSERT другая транзакция успевает вставить своё. Exclusion constraint проверяется внутри
   базы атомарно относительно всех транзакций. Тест показал 4 пересечения из 16 без него.
2. **Откуда дедлоки при exclusion constraint и почему не ретрай?** Вставка ждёт незакоммиченную
   конфликтующую строку, ожидания образуют цикл, и Postgres убивает одну транзакцию (40P01). При 16
   конкурентах ретраи снова дедлочатся. Advisory lock по courier_id выстраивает их в очередь заранее.
3. **Почему advisory lock в CTE, а не отдельным запросом?** Тот же statement и та же транзакция, без
   лишнего round trip. Лок `xact` снимается при commit/rollback сам.
4. **Зачем `FOR SHARE` при записи доставки?** Чтобы конкурентная отмена смены (UPDATE строки) ждала,
   пока доставка не запишется, и не появилась доставка в отменённой смене.
5. **Как устроен кэш и что с консистентностью?** Ключ на курьеро-день, MGET на чтение, SET EX на
   заполнение, DEL дня на запись. Известная дыра: читатель, сходивший в базу до записи, может положить
   устаревший день после инвалидации, и он проживёт до TTL (60 с). Лечится версией в ключе. Это записано
   в ограничениях.
6. **Почему деньги не кэшируются?** Кэшируются агрегаты работы (часы, доставки, км), деньги считаются
   на запрос по текущему тарифу. Смена тарифа в dynamic config не требует сброса кэша.
7. **Что показал флеймграф и как проверили эффект?** Ручка заработка заняла 19% CPU, в основном промахи
   кэша (hit rate 17%). После кэша по дням: hit rate 60%, CPU сервиса −12% на 12k RPS. По 3 прогона
   до и после на одном стенде, плюс счётчики Redis и Postgres.
8. **Зачем congestion control, если он режет запросы?** Без него перегрузка заканчивается коллапсом:
   очередь пула Postgres переполняется, отвечают меньше, чем ёмкость. С CC сервер рано отдаёт 429, 5xx
   нет, p99 около 23 мс. Минус: на VM дефолтная политика режет лишнее, это следующий шаг.
9. **Что за баг в userver и почему его не поймали тесты userver?** `CpuLimit()` возвращает 0 вместо
   nullopt, поэтому `IsInRtc()` всегда true, и CC молча уходит в fake-mode. Тестов на `cpu_limit.cpp` не
   было, а функция кэширует результат в static и читает реальные `/proc` и env, поэтому тестировать её
   неудобно. Фикс вынес пути в параметры и добавил тест с фейковыми файлами cgroup.
10. **Зачем TSan в Docker нужен `seccomp=unconfined`?** TSan перезапускает себя с
    `personality(ADDR_NO_RANDOMIZE)`, когда ASLR мешает его теневой памяти, а дефолтный seccomp Docker
    это запрещает.
